## FASE 2 · Escaneo de vulnerabilidades de imágenes (Trivy)

### Qué se implementó

| Pieza | Archivo | Función |
|---|---|---|
| Escáner y compuerta | [security/scan-images.sh](../../security/scan-images.sh) | Ejecuta Trivy en un contenedor, genera JSON y SARIF por imagen, resume y decide si bloquea |
| Política | [security/policy.env](../../security/policy.env) | Umbral de severidad, versión de Trivy (por tag y digest) y reglas para terceros. Todo se puede sobrescribir por variable de entorno |
| Catálogo | [security/images.catalog](../../security/images.catalog) | 13 imágenes de terceros (runtime y observabilidad) |
| Pruebas de la compuerta | [security/tests/test-gate.sh](../../security/tests/test-gate.sh) | 14 casos sin red ni Docker, con informes sintéticos de [fixtures](../../security/tests/fixtures/README.md) |

Las 9 imágenes propias salen de [deploy/lib.sh](../../deploy/lib.sh) (8 servicios y el cliente web), así que no se duplica su lista.
Trivy corre como contenedor `aquasec/trivy:0.76.1` fijado por digest; no se instala nada en la máquina ni se acepta ningún EULA
(Trivy es Apache-2.0).

### Cómo ejecutarlo

Requiere Docker, bash (WSL, Linux o un agente de Jenkins) y red para descargar la base de vulnerabilidades.

```bash
# 1) Construir las imágenes (ya existente, HU-02)
./deploy/build-images.sh 1.0.0

# 2) Escanear las 9 imágenes propias (bloquean) y las 13 de terceros (se reportan)
./security/scan-images.sh --own 1.0.0 --third-party

# Otras formas
./security/scan-images.sh --image <referencia> [--class own|third-party]
./security/scan-images.sh --evaluate security/reports/<informe>.json --class own   # solo la compuerta, sin red
TRIVY_SEVERITY_BLOCK=CRITICAL ./security/scan-images.sh --own 1.0.0                # otro umbral
./security/tests/test-gate.sh                                                      # pruebas de la compuerta
```

**Código de salida:** `0` = nada bloquea · `1` = una imagen que bloquea supera el umbral · `2` = un escaneo, un informe o la
configuración falló. Un escaneo que no se pudo ejecutar **nunca** cuenta como aprobado.

### Cómo interpretar los resultados

Los informes quedan en `security/reports/` (no se versionan por su tamaño: entre 1 y 7 MB cada uno):

| Archivo | Contenido |
|---|---|
| `<clase>_<imagen>.json` | Informe completo de Trivy, todas las severidades |
| `<clase>_<imagen>.sarif` | El mismo informe en SARIF, para visores o GitHub code scanning |
| `summary-<fecha>.txt` / `.tsv` | Una línea por imagen: estado, clase, imagen y conteo de CRITICAL, HIGH, MEDIUM, LOW y UNKNOWN |

Estados de la línea de resumen: `PASS` (sin hallazgos que bloqueen), `FAIL` (la imagen bloquea la promoción),
`REPORT-ONLY` (tiene hallazgos que bloquearían, pero es de terceros y la política no los hace bloquear) y `ERROR`.
El conteo son *instancias* (un mismo CVE en dos paquetes cuenta dos veces).

### Política de umbrales

- **Bloquean:** CRITICAL y HIGH (criterio inicial de HU-14; el proyecto no tenía una política previa).
- **No se oculta nada.** El informe lista todas las severidades. `TRIVY_IGNORE_UNFIXED` está en `false`; si alguien lo pone en
  `true`, quedan fuera del informe las vulnerabilidades sin arreglo, y eso debe justificarse por escrito.
- **No hay exclusiones** (ni archivo `.trivyignore`) en esta fase.
- **Imágenes de terceros** (bases de datos, Kafka, observabilidad): se escanean y se reportan completas, pero **no bloquean** por
  defecto (`TRIVY_BLOCK_THIRD_PARTY=false`). Motivo: CircleGuard no puede parchear una imagen ajena; solo puede actualizarla o
  reemplazarla, y esas decisiones son de otras historias. Esto responde a la petición de que Trivy no bloquee por las imágenes de
  observabilidad (HU-13), pero sus hallazgos siguen visibles. Se revierte con `TRIVY_BLOCK_THIRD_PARTY=true`.

### Decisión pendiente que esto provoca

Con la política CRITICAL y HIGH, **la compuerta bloquearía todas las promociones**, y bajar el umbral a solo CRITICAL no lo evita
(126 CRITICAL en las imágenes propias). Las opciones son técnicas y de equipo:

1. **Corregir las causas.** Actualizar la base de las imágenes (o `apk upgrade` en cada Dockerfile) elimina los 468 hallazgos de
   paquetes del sistema. Subir Spring Boot a una línea con parches elimina la mayoría de los 423 de bibliotecas. Los Dockerfiles son de
   HU-02 y la versión de Spring Boot afecta a todos los servicios, así que no se cambiaron aquí.
2. **Línea base con caducidad.** Aceptar por escrito los hallazgos actuales, con responsable y fecha, y bloquear solo los *nuevos*.
   No está implementado; requeriría un archivo de excepciones justificado.
3. **Compuerta informativa temporal.** Publicar los informes sin bloquear hasta corregir. Es el menos protector y debe quedar como
   excepción declarada, no como política.

### Integración con Jenkins (no aplicada)

El [Jenkinsfile](../../Jenkinsfile) no se ha modificado. El punto de integración es una etapa entre *Package images* y *Publish images*:

```groovy
stage('Image vulnerability scan') {
  when {
    allOf {
      expression { params.BUILD_IMAGES }
      expression { !params.ROLLBACK_VERSION?.trim() }
      anyOf { branch 'dev'; branch 'main'; expression { params.FORCE_PROD } }
    }
  }
  steps { sh "./security/scan-images.sh --own '${env.VERSION}' --third-party" }
  post  { always { archiveArtifacts artifacts: 'security/reports/**', allowEmptyArchive: true } }
}
```

Dos cuidados antes de aplicarla:

- El script monta `/var/run/docker.sock` para leer imágenes locales. El agente de Jenkins usa `DOCKER_HOST=tcp://dind:2375`, así que habrá
  que pasar esa variable al contenedor de Trivy y darle acceso a esa red. **No se ha probado en el agente.**
- Con los resultados actuales, la etapa pondría el pipeline en rojo en cada ejecución (ver la decisión pendiente).

### Limitaciones

- Se ejecutó en la máquina del autor (WSL), no en Jenkins.
- La base de vulnerabilidades se descarga de `mirror.gcr.io/aquasec/trivy-db`; en un agente sin salida a Internet hace falta un espejo
  (`TRIVY_SKIP_DB_UPDATE=true` reutiliza la caché).
- Trivy se ejecutó solo con el escáner de vulnerabilidades. Los secretos y la configuración errónea de los Dockerfiles no se analizan aquí.
- Los conteos dependen de la fecha de la base de datos: repetir el escaneo otro día puede dar otras cifras.
- No se escanearon las imágenes de herramientas del pipeline (Jenkins, SonarQube, registro, Nexus; HU-01).

### Corrección de HU-04/HU-13: causa y seguridad

- **Causa raíz:** HU-13 añadió Actuator, que registra por defecto `managementSecurityFilterChain`; ese bean exige un `HttpSecurity`, que solo existe si Spring Security está activo.
  El contexto de notification de las pruebas excluye Spring Security, pero comparte classpath con promotion, que sí lo trae. El servicio de notification
  **no tiene Spring Security en producción** ([build.gradle.kts](../../services/circleguard-notification-service/build.gradle.kts)), así que allí esa autoconfiguración no se activa nunca.
- **Por qué es segura:** la exclusión solo quita la cadena de seguridad por defecto de Actuator en ese contexto de pruebas, donde Spring Security ya estaba excluido por completo.
  No hay reglas de autenticación ni de autorización que se oculten. El contexto de promotion, que sí tiene seguridad, no cambia.
- **Verificación:** las 3 clases que fallaban y las 6 de promotion pasan (17 en total). La seguridad de producción no cambió: el diff no toca ningún archivo de `src/main`.
  Actuator sigue funcionando en los contenedores (`/actuator/health` y `/actuator/prometheus` responden y la métrica del circuit breaker está publicada).

**Resultados reales (2026-11-17).**

## FASE 7 · TLS

**Qué servicios necesitan TLS.** En Compose solo el cliente web publica un puerto (el resto es red interna), así que el cifrado hacia fuera se termina en un proxy delante de él. En Kubernetes serían los Ingress del cliente web y de Grafana.
El tráfico entre servicios dentro de la red de Compose sigue siendo HTTP; no se cambió.

| Pieza | Archivo | Estado |
|---|---|---|
| Certificados de **desarrollo** con CA propia (ECDSA P-256, 30 días), claves fuera de Git | [gen-dev-cert.sh](../../security/tls/gen-dev-cert.sh) | Probado |
| Terminador TLS: TLS 1.2 y 1.3, cifrados AEAD con confidencialidad directa, HSTS, redirección de HTTP a HTTPS | [nginx-tls.conf](../../security/tls/nginx-tls.conf) | Probado con un servidor real |
| Overlay de Compose (no modifica los de HU-02), con el certificado montado desde fuera del repositorio | [docker-compose.tls.yml](../../security/tls/docker-compose.tls.yml) | Preparado; **no probado con el stack completo** |
| Verificación de cadena, nombre, vigencia, protocolos y HSTS | [verify-tls.sh](../../security/tls/verify-tls.sh) | Probado |
| **Ingress de HU-10 (Traefik) con la sección `tls`** y Secret autofirmado | [componente](../../deploy/k8s/components/tls/kustomization.yaml), [ensure-tls-secret.sh](../../security/k8s/tls/ensure-tls-secret.sh) | Render y esquema válidos; script con 21 pruebas; **no aplicado en un clúster** (FASE 10) |
| Referencia de cert-manager y de Grafana (asumía ingress-nginx; **el clúster de HU-10 usa Traefik**) | [ingress-tls.yaml](../../security/k8s/tls/ingress-tls.yaml), [certificate.yaml](../../security/k8s/tls/certificate.yaml) | Solo como referencia; `Certificate` **sin validar** (CRD) |

**Prueba real** ([test-tls.sh](../../security/tests/test-tls.sh), 8 de 8, [evidencia](../evidencias/hu-14/fase7/01-pruebas-tls-con-servidor-real.txt)): con el certificado de desarrollo, el terminador pasa los 8 controles (cadena válida con su CA, nombre correcto, vigencia, TLS 1.3 y 1.2 aceptados, TLS 1.1 y 1.0 rechazados, HSTS);
y **fallan, como deben**, una CA distinta, un nombre que no está en el certificado, una vigencia insuficiente y el almacén de confianza del sistema. HTTP solo redirige a HTTPS y la aplicación responde a través de TLS.
El primer intento de `verify-tls.sh` daba falsos positivos (aceptaba un nombre equivocado); la prueba lo detectó y se corrigió.

**Renovación de certificados.**
- *Compose con certificado real:* sustituir `fullchain.pem` y `server.key` en `CG_TLS_DIR` y recargar sin reiniciar: `docker compose exec tls-proxy nginx -s reload`. La clave debe poder leerla el usuario 101 del contenedor.
- *Desarrollo:* volver a ejecutar `gen-dev-cert.sh` (30 días de vigencia).
- *Kubernetes:* cert-manager renueva solo cuando faltan 30 días ([certificate.yaml](../../security/k8s/tls/certificate.yaml)) y actualiza el Secret que usa el Ingress.
- *Vigilancia:* ejecutar `verify-tls.sh <host> 443 --min-days 14` de forma periódica, por ejemplo en un trabajo de Jenkins, para detectar un certificado a punto de caducar.

**Lo que NO se afirma.** TLS **no está desplegado**: no hay certificado real ni dominio, y el Ingress de HU-10 todavía no se aplicó con `tls` en un clúster. Lo demostrado es el terminador y la verificación con un certificado de desarrollo, y que el componente de Traefik y el script del Secret funcionan sin clúster. HTTP no se redirige a HTTPS en Kubernetes (hace falta un `Middleware` de Traefik que se debe probar en el clúster).

**2. Defecto del proxy, corregido.** Al probar la imagen se descubrió que `mobile/nginx.conf` **perdía la ruta de cada petición**: con una variable en `proxy_pass`, nginx no recorta el prefijo y reenvía siempre `/`, así que `/auth/api/v1/auth/login` llegaba al servicio como `/`.

La corrección añade un `rewrite ^/<servicio>/(.*)$ /$1 break;` a cada uno de los ocho prefijos y conserva la resolución dinámica de DNS. La prueba [deploy/test-web-proxy.sh](../../deploy/test-web-proxy.sh) lo comprueba con un servicio de prueba por prefijo:
**antes, falla** (cada servicio recibía `/`); **después, 14 de 14** (ruta completa, query string, rutas anidadas y POST) ([evidencia](../evidencias/hu-14/hu01-hu02/04-web-proxy-regresion.txt)).

`/identity/actuator/health` responde 200 UP a través del proxy. En esa ocasión solo se probó lo que atraviesa `auth` e `identity`. **Actualización 2026-11-20:** con el stack completo (15/15 healthy) el login **exitoso** del usuario de prueba a través del proxy da 200 con token; el 401 anterior era un error de mi prueba (ver FASE 3b y la [evidencia](../evidencias/hu-14/correcciones/06-login-extremo-a-extremo.txt)).

## FASE 9 · Excepciones de vulnerabilidades con caducidad

Los 3 CRITICAL y 22 HIGH que dependen de Spring Boot 4 (FASE 3b) no se pueden corregir ahora. En vez de bajar el umbral, la compuerta admite **excepciones puntuales con caducidad**. No se hace ninguna excepción todavía: el archivo activo está vacío.

| Regla | Valor |
|---|---|
| Plazo máximo desde la aprobación | CRITICAL 30 días · HIGH 90 días (`EXCEPTION_MAX_DAYS_*`) |
| Revisión obligatoria | CRITICAL cada 14 días · HIGH cada 30 (`EXCEPTION_REVIEW_DAYS_*`); la excepción vale mientras `hoy <= last_review + intervalo` |
| Campos obligatorios | id, paquete, ámbito (imagen o `deps:<servicio>`), severidad, responsable, justificación técnica (≥ 20 caracteres), approved, last_review, expires |
| Alcance | Un hallazgo identificado: coinciden **id + paquete + ámbito + severidad**. Una vulnerabilidad nueva, otro paquete, otra imagen o una severidad mayor **no** coincide |
| Prohibido | Comodines, `all`/`any`, exclusiones globales, excepciones sin caducidad, responsable o justificación `PENDIENTE` |
| Caducada o con revisión vencida | Deja de ser válida y la compuerta vuelve a bloquear (aviso en la salida). Se aplica a CRITICAL y a HIGH |
| Entrada que incumple las reglas | Error de configuración (código 2), nunca se ignora en silencio |

Los informes de Trivy (JSON/SARIF), los contadores y el resumen **siguen listando todas las vulnerabilidades**; la excepción solo cambia si bloquean. La salida indica `[excepciones vigentes: N]` y, por cada una, responsable y fecha de caducidad. Los umbrales (`CRITICAL,HIGH`) no cambian. Para renovar una excepción hay que abrir un cambio que mueva `last_review` (y respete `expires`); queda en el historial de Git.

**Ejemplos reales** ([salida completa](../evidencias/hu-14/excepciones.md)), con un informe sintético con un CRITICAL y un HIGH y fecha fija 2026-11-20:

| Caso | Resultado |

| Excepción del CRITICAL caducada ayer | `FAIL`, código 1, con el aviso `CADUCADA` |
| Solo el HIGH exceptuado; el CRITICAL es nuevo | `FAIL`, código 1 |

**Pruebas:** 29 casos (vigente, caduca hoy, caducada, revisión vencida CRITICAL y HIGH, otro paquete/imagen/severidad, comodín, ámbito global, sin responsable, sin caducidad, `PENDIENTE`, justificación corta, plazos de 30/31 y 90/91 días, fechas inválidas, columnas erróneas, umbrales sin cambios, informe no modificado, archivo entregado sin exenciones).
