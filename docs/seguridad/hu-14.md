## FASE 2 · Escaneo de vulnerabilidades de imágenes (Trivy)

### Qué se implementó

| Pieza | Archivo | Función |
|---|---|---|
| Escáner y compuerta | [security/scan-images.sh](../../security/scan-images.sh) | Ejecuta Trivy en un contenedor, genera JSON y SARIF por imagen, resume y decide si bloquea |
| Política | [security/policy.env](../../security/policy.env) | Umbral de severidad, versión de Trivy (por tag y digest) y reglas para terceros. Todo se puede sobrescribir por variable de entorno |
| Catálogo | [security/images.catalog](../../security/images.catalog) | 13 imágenes de terceros (runtime y observabilidad) |
| Pruebas de la compuerta | [security/tests/test-gate.sh](../../security/tests/test-gate.sh) | 14 casos sin red ni Docker, con informes sintéticos de [fixtures](../../security/tests/fixtures/README.md) |

Las 9 imágenes propias salen de [deploy/lib.sh](../../deploy/lib.sh) (8 servicios y el cliente web), así que no se duplica su lista.
Trivy corre como contenedor `aquasec/trivy:0.76.1` fijado por digest; no se instala nada en la máquina ni se acepta ningún EULA
(Trivy es Apache-2.0).

### Cómo ejecutarlo

Requiere Docker, bash (WSL, Linux o un agente de Jenkins) y red para descargar la base de vulnerabilidades.

```bash
# 1) Construir las imágenes (ya existente, HU-02)
./deploy/build-images.sh 1.0.0

# 2) Escanear las 9 imágenes propias (bloquean) y las 13 de terceros (se reportan)
./security/scan-images.sh --own 1.0.0 --third-party

# Otras formas
./security/scan-images.sh --image <referencia> [--class own|third-party]
./security/scan-images.sh --evaluate security/reports/<informe>.json --class own   # solo la compuerta, sin red
TRIVY_SEVERITY_BLOCK=CRITICAL ./security/scan-images.sh --own 1.0.0                # otro umbral
./security/tests/test-gate.sh                                                      # pruebas de la compuerta
```

**Código de salida:** `0` = nada bloquea · `1` = una imagen que bloquea supera el umbral · `2` = un escaneo, un informe o la
configuración falló. Un escaneo que no se pudo ejecutar **nunca** cuenta como aprobado.

### Cómo interpretar los resultados

Los informes quedan en `security/reports/` (no se versionan por su tamaño: entre 1 y 7 MB cada uno):

| Archivo | Contenido |
|---|---|
| `<clase>_<imagen>.json` | Informe completo de Trivy, todas las severidades |
| `<clase>_<imagen>.sarif` | El mismo informe en SARIF, para visores o GitHub code scanning |
| `summary-<fecha>.txt` / `.tsv` | Una línea por imagen: estado, clase, imagen y conteo de CRITICAL, HIGH, MEDIUM, LOW y UNKNOWN |

Estados de la línea de resumen: `PASS` (sin hallazgos que bloqueen), `FAIL` (la imagen bloquea la promoción),
`REPORT-ONLY` (tiene hallazgos que bloquearían, pero es de terceros y la política no los hace bloquear) y `ERROR`.
El conteo son *instancias* (un mismo CVE en dos paquetes cuenta dos veces).

### Política de umbrales

- **Bloquean:** CRITICAL y HIGH (criterio inicial de HU-14; el proyecto no tenía una política previa).
- **No se oculta nada.** El informe lista todas las severidades. `TRIVY_IGNORE_UNFIXED` está en `false`; si alguien lo pone en
  `true`, quedan fuera del informe las vulnerabilidades sin arreglo, y eso debe justificarse por escrito.
- **No hay exclusiones** (ni archivo `.trivyignore`) en esta fase.
- **Imágenes de terceros** (bases de datos, Kafka, observabilidad): se escanean y se reportan completas, pero **no bloquean** por
  defecto (`TRIVY_BLOCK_THIRD_PARTY=false`). Motivo: CircleGuard no puede parchear una imagen ajena; solo puede actualizarla o
  reemplazarla, y esas decisiones son de otras historias. Esto responde a la petición de que Trivy no bloquee por las imágenes de
  observabilidad (HU-13), pero sus hallazgos siguen visibles. Se revierte con `TRIVY_BLOCK_THIRD_PARTY=true`.

### Decisión pendiente que esto provoca

Con la política CRITICAL y HIGH, **la compuerta bloquearía todas las promociones**, y bajar el umbral a solo CRITICAL no lo evita
(126 CRITICAL en las imágenes propias). Las opciones son técnicas y de equipo:

1. **Corregir las causas.** Actualizar la base de las imágenes (o `apk upgrade` en cada Dockerfile) elimina los 468 hallazgos de
   paquetes del sistema. Subir Spring Boot a una línea con parches elimina la mayoría de los 423 de bibliotecas. Los Dockerfiles son de
   HU-02 y la versión de Spring Boot afecta a todos los servicios, así que no se cambiaron aquí.
2. **Línea base con caducidad.** Aceptar por escrito los hallazgos actuales, con responsable y fecha, y bloquear solo los *nuevos*.
   No está implementado; requeriría un archivo de excepciones justificado.
3. **Compuerta informativa temporal.** Publicar los informes sin bloquear hasta corregir. Es el menos protector y debe quedar como
   excepción declarada, no como política.

### Integración con Jenkins (no aplicada)

El [Jenkinsfile](../../Jenkinsfile) no se ha modificado. El punto de integración es una etapa entre *Package images* y *Publish images*:

```groovy
stage('Image vulnerability scan') {
  when {
    allOf {
      expression { params.BUILD_IMAGES }
      expression { !params.ROLLBACK_VERSION?.trim() }
      anyOf { branch 'dev'; branch 'main'; expression { params.FORCE_PROD } }
    }
  }
  steps { sh "./security/scan-images.sh --own '${env.VERSION}' --third-party" }
  post  { always { archiveArtifacts artifacts: 'security/reports/**', allowEmptyArchive: true } }
}
```

Dos cuidados antes de aplicarla:

- El script monta `/var/run/docker.sock` para leer imágenes locales. El agente de Jenkins usa `DOCKER_HOST=tcp://dind:2375`, así que habrá
  que pasar esa variable al contenedor de Trivy y darle acceso a esa red. **No se ha probado en el agente.**
- Con los resultados actuales, la etapa pondría el pipeline en rojo en cada ejecución (ver la decisión pendiente).

### Limitaciones

- Se ejecutó en la máquina del autor (WSL), no en Jenkins.
- La base de vulnerabilidades se descarga de `mirror.gcr.io/aquasec/trivy-db`; en un agente sin salida a Internet hace falta un espejo
  (`TRIVY_SKIP_DB_UPDATE=true` reutiliza la caché).
- Trivy se ejecutó solo con el escáner de vulnerabilidades. Los secretos y la configuración errónea de los Dockerfiles no se analizan aquí.
- Los conteos dependen de la fecha de la base de datos: repetir el escaneo otro día puede dar otras cifras.
- No se escanearon las imágenes de herramientas del pipeline (Jenkins, SonarQube, registro, Nexus; HU-01).
